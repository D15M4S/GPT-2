## Q1. BPE(Byte Pair Encoding)란 무엇인가? ⭐

<details>
<summary>▶ 답</summary>

**자주 붙어 나오는 바이트 쌍을 반복적으로 하나로 합쳐 어휘집을 만드는 알고리즘.**

핵심 직관: "자주 같이 나오는 것은 하나로 묶자."

```
텍스트: "aaabdaaabac"

초기:  a a a b d a a a b a c
1회:   aa a b d aa a b a c     ← 'aa'가 가장 빈번 → 합침
2회:   aaa b d aaa b a c       ← 'aaa'로 다시 합침 (실제로는 aa+a)
3회:   aaab d aaab a c         ← 'aaab'로 합침
```

최종적으로 원래 11개 토큰이 5개로 압축된다.

</details>

## Q2. BPE는 왜 256 바이트에서 시작하는가? ⭐

<details>
<summary>▶ 답</summary>

**UTF-8로 인코딩하면 어떤 언어·문자도 결국 0~255 사이의 바이트들로 표현되기 때문.**

```python
"A".encode('utf-8')    →  b'\x41'       (1바이트: 65)
"한".encode('utf-8')   →  b'\xed\x95\x9c'  (3바이트: 237, 149, 156)
"😀".encode('utf-8')   →  b'\xf0\x9f\x98\x80' (4바이트)
```

- 256개 기본 토큰(0~255)만 있으면 세상의 모든 텍스트를 표현 가능
- **OOV가 원천적으로 불가능** — 어떤 입력이 들어와도 바이트로 쪼개면 항상 처리됨
- BPE 학습은 이 256개 바이트 위에서 "자주 붙어 나오는 쌍"을 합쳐 새 토큰을 추가하는 방식

</details>

## Q3. BPE 학습(train) 과정을 단계별로 설명하라. ⭐⭐

<details>
<summary>▶ 답</summary>

```
입력: 학습 텍스트, 목표 vocab_size
출력: 병합 규칙(merges) 사전
```

**1단계**: 텍스트를 UTF-8 바이트로 변환 → 초기 ID 목록 (0~255)

**2단계**: `get_stats()` — 인접한 모든 쌍의 등장 횟수를 센다

```python
[97, 97, 98]  →  {(97,97): 1, (97,98): 1}
```

**3단계**: 가장 빈번한 쌍을 선택, 새 ID를 부여 (256번부터 시작)

**4단계**: `merge()` — ID 목록 전체에서 해당 쌍을 새 ID로 교체

**5단계**: vocab_size에 도달할 때까지 2~4를 반복

```
병합 규칙 예시:
(101, 32)  →  256  ('e ')
(32, 116)  →  257  (' t')
(257, 104) →  258  (' th')
(258, 256) →  259  (' the ')
```

</details>

## Q4. `get_stats()`와 `merge()`의 역할을 각각 설명하라. ⭐⭐

<details>
<summary>▶ 답</summary>

**`get_stats(ids)`**
- 역할: ID 목록에서 인접한 쌍의 등장 횟수를 세어 딕셔너리로 반환
- BPE의 핵심 질문 "가장 자주 붙어 나오는 쌍은 무엇인가?"에 답하는 함수

```python
get_stats([1, 2, 1, 2, 3])
→ {(1,2): 2, (2,1): 1, (2,3): 1}
```

**`merge(ids, pair, new_id)`**
- 역할: ID 목록에서 특정 쌍을 찾아 전부 새 ID로 교체한 목록 반환
- "병합"을 실제로 수행하는 함수

```python
merge([1, 2, 3, 1, 2, 4], pair=(1,2), new_id=10)
→ [10, 3, 10, 4]
```

두 함수가 교대로 반복 실행되며 BPE 학습이 진행된다.

</details>

## Q5. BPE 인코딩(encode) 과정은 어떻게 동작하는가? ⭐⭐

<details>
<summary>▶ 답</summary>

학습 때 만든 **병합 규칙을 순서대로 적용**한다.

```
인코딩 대상: "the"
UTF-8 바이트: [116, 104, 101]  (t=116, h=104, e=101)

병합 규칙 적용 (학습된 순서대로):
1. (101, 32) → 256: 해당 쌍 없음, 스킵
2. (32, 116) → 257: 해당 쌍 없음, 스킵
3. (116, 104) → 258: (116,104) 발견! → [258, 101]
4. (258, 101) → 259: (258,101) 발견! → [259]

최종 결과: [259]  ← "the"가 단 1개의 토큰으로 표현됨
```

병합 규칙은 **학습 때의 순서**대로 적용해야 하며, 순서가 달라지면 결과가 바뀐다.

</details>

## Q6. vocab_size를 크게 설정하면 어떤 장단점이 있는가? ⭐⭐

<details>
<summary>▶ 답</summary>

**vocab_size를 크게 하면**
- 자주 쓰는 단어·구문이 단일 토큰으로 표현됨 → 시퀀스 짧아짐 → 모델 처리 효율 향상
- 더 많은 정보를 하나의 토큰에 담을 수 있음

**단점**
- 임베딩 행렬이 커짐 → 메모리·파라미터 증가
- 희귀 토큰은 학습 데이터에 거의 안 나와 임베딩이 제대로 학습되지 않음

**vocab_size를 작게 하면**
- 모델이 가벼워짐
- 자주 쓰는 단어도 서브워드로 쪼개짐 → 시퀀스 길어짐 → 처리 비용 증가

**실무 기준**
| 모델 | vocab_size |
|---|---|
| GPT-2 | 50,257 |
| GPT-4 (tiktoken) | 100,277 |
| LLaMA-3 | 128,256 |

약 50,000~100,000 수준이 현재 실무의 표준 범위다.

</details>

## Q7. BPE가 char/word 방식보다 나은 이유를 한 문장으로 정리하라. ⭐⭐

<details>
<summary>▶ 답</summary>

**"OOV 없이(바이트 기반) + 짧은 시퀀스(빈번한 패턴 병합) + 적당한 vocab_size(~50K)"를 동시에 달성하기 때문.**

| | 글자 단위 | 단어 단위 | BPE |
|---|---|---|---|
| OOV | 거의 없음 | 빈번 | **없음** |
| 시퀀스 길이 | 매우 김 | 짧음 | **중간** |
| vocab_size | 매우 작음 | 너무 큼 | **적당함** |
| 의미 보존 | 낮음 | 높음 | **중간~높음** |

</details>

## Q8. BPE encode와 decode는 서로 역방향인가? ⭐⭐

<details>
<summary>▶ 답</summary>

**Yes, 완벽하게 역방향이며 항상 원본이 복원된다.**

- encode: 텍스트 → UTF-8 바이트 → 병합 규칙 적용 → ID 목록
- decode: ID 목록 → 각 ID에 해당하는 bytes 조각 → bytes 이어 붙이기 → UTF-8 디코딩 → 텍스트

```python
ids = tokenizer.encode("hello 안녕")
text = tokenizer.decode(ids)
assert text == "hello 안녕"  # 항상 True
```

BPE는 256 바이트에서 시작하므로 **어떤 입력이 들어와도 OOV 없이 인코딩되고 완벽히 복원**된다.  
이것이 글자/단어 단위와의 가장 큰 차별점이다.

</details>

## Q9. BasicTokenizer의 한계는 무엇인가? RegexTokenizer는 어떻게 해결하는가? ⭐⭐⭐

<details>
<summary>▶ 답</summary>

**BasicTokenizer의 한계: 단어 경계를 무시한 병합**

```
"New York is great"를 학습할 때:
'k'와 ' '와 'i'가 자주 붙어 나오면 "k i" → 하나의 토큰이 될 수 있음
→ "York is"라는 단어 경계를 무시한 비직관적인 토큰 생성
```

또한 축약형도 문제:
```
"don't" → 'd', 'o', 'n', "'", 't'
"'"와 't'가 병합되어 이상한 토큰이 생길 수 있음
```

**RegexTokenizer의 해결책: 먼저 정규식으로 자른 뒤 BPE 적용**

```python
# GPT-4가 사용하는 패턴 (tiktoken)
pattern = r"""(?i:'s|'t|'re|'ve|'m|'ll|'d)|
              [^\r\n\p{L}\p{N}]?\p{L}+|
              \p{N}{1,3}|
              [^\s\p{L}\p{N}]+|
              \s+"""
```

- 축약형('s, 't, 're...)을 먼저 분리
- 글자/숫자/구두점 카테고리 간 경계를 넘어서는 병합을 원천 차단
- 숫자는 최대 3자리씩 분리 ("1234" → "123", "4")

결과: 더 일관성 있고 직관적인 토큰이 생성된다.

</details>

## Q10. tiktoken과 BPE의 관계는? GPT-2와 GPT-4의 차이는? ⭐⭐⭐

<details>
<summary>▶ 답</summary>

**tiktoken은 OpenAI가 만든 BPE 기반 토크나이저 라이브러리.**

- 내부 알고리즘은 BPE이지만, C로 구현되어 Python BPE보다 수십 배 빠름
- RegexTokenizer 방식으로 단어 경계를 사전에 처리함

**GPT-2 vs GPT-4 차이**

| 항목 | GPT-2 | GPT-4 (tiktoken) |
|---|---|---|
| vocab_size | 50,257 | 100,277 |
| 정규식 패턴 | 단순 (영어 중심) | 다국어 지원 (`\p{L}`, `\p{N}`) |
| 특수 토큰 | `<\|endoftext\|>` 1개 | 여러 개 |
| 숫자 처리 | 그대로 병합 | 최대 3자리로 분리 |

GPT-4는 vocab_size가 2배라 더 짧은 시퀀스로 같은 텍스트를 표현할 수 있고,  
다국어 텍스트(한국어 포함)를 훨씬 효율적으로 처리한다.

</details>

## Q11. 같은 텍스트를 vocab_size=300으로 학습했을 때와 vocab_size=1000으로 학습했을 때의 차이는? ⭐⭐⭐

<details>
<summary>▶ 답</summary>

**vocab_size가 클수록 더 많은 병합이 일어나 시퀀스가 짧아진다.**

```
"the quick brown fox"

vocab_size=300 (병합 44회):
→ [' the', ' quick', ' brown', ' fox'] 정도 수준 (단어 근접)

vocab_size=1000 (병합 744회):
→ [' the quick', ' brown fox'] 처럼 자주 등장하는 구문도 단일 토큰화 가능
```

- vocab_size=300: 자주 쓰는 바이트 쌍만 합침, 대부분은 서브워드
- vocab_size=1000: 빈번한 단어 전체가 단일 토큰화, 구문(phrase)까지 합쳐짐

**압축 비율**: vocab_size가 클수록 인코딩 후 토큰 수가 줄어드는 비율(압축률)이 높아진다.  
실제로 basic_tokenizer.py 테스트에서 압축 비율 약 1.6배를 확인했다.

</details>

## Q12. BPE 학습 결과물로 무엇이 저장되는가? 왜 그것을 저장하는가? ⭐⭐

<details>
<summary>▶ 답</summary>

**두 가지가 저장된다.**

**1. `.model` 파일 — 병합 규칙(merges)**
```
256 101 32    ← ID 256 = 바이트 101('e')과 바이트 32(' ')의 병합
257 32 116    ← ID 257 = 바이트 32(' ')과 바이트 116('t')의 병합
...
```

**2. `.vocab` 파일 — 어휘집**
```
256: e        ← 사람이 읽기 편한 형태로 확인용
257:  t
...
```

**왜 병합 규칙을 저장하는가?**  
인코딩 시 병합 규칙을 **학습 때와 동일한 순서**로 적용해야 하기 때문.  
순서가 달라지면 다른 결과가 나오고, 모델이 학습한 ID와 불일치가 발생한다.

어휘집(.vocab)은 확인·디버깅용이며, 실제 인코딩/디코딩에 사용되는 것은 .model 파일이다.

</details>
