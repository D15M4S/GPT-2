# 01. 토크나이저란 무엇인가?

## 목표

이 문서를 읽고 나면 다음 질문에 답할 수 있게 됩니다.

- 컴퓨터는 왜 글자를 그대로 이해하지 못하는가?
- 토크나이저는 어떤 역할을 하는가?
- 토큰(Token)이란 무엇인가?
- 왜 단순히 글자 하나하나로 쪼개면 안 되는가?

---

## 1. 컴퓨터는 숫자만 이해한다

컴퓨터는 오직 숫자만 이해할 수 있습니다.

"안녕하세요"라는 문장을 컴퓨터에게 그대로 보여주면, 컴퓨터는 이것을 처리할 수 없습니다.
반드시 숫자로 바꾸어 주어야 합니다.

예를 들어, "안녕하세요"를 숫자로 바꾼다면 이런 식입니다.

```
"안녕하세요"  →  [12, 34, 56, 78, 90]
```

이렇게 **문장을 숫자 목록으로 변환하는 과정** 전체를 **토크나이징(Tokenizing)** 이라고 하고,
그 역할을 하는 도구를 **토크나이저(Tokenizer)** 라고 합니다.

---

## 2. 비유로 이해하기 — 악보와 음표

음악을 생각해 보세요.

- 우리가 듣는 음악은 소리입니다.
- 하지만 작곡가는 소리를 직접 전달할 수 없으니, **악보**라는 약속된 기호 체계로 표현합니다.
- 연주자는 악보(기호)를 보고 소리(음악)로 변환합니다.

토크나이저도 마찬가지입니다.

- 우리가 쓰는 언어는 "소리" 같은 존재입니다.
- 컴퓨터(AI)는 그 언어를 직접 이해할 수 없습니다.
- 토크나이저는 언어를 **컴퓨터가 읽을 수 있는 악보(숫자 목록)** 로 변환해줍니다.

```
[우리의 언어]  →  토크나이저  →  [숫자 목록]  →  AI 모델
```

---

## 3. 토큰(Token)이란?

토크나이저가 문장을 쪼갤 때, 그 쪼개진 조각 하나하나를 **토큰(Token)** 이라고 합니다.

어떻게 쪼개느냐에 따라 토큰의 단위가 달라집니다.

| 방식 | 문장 | 토큰 목록 |
|---|---|---|
| 글자 단위 | "hello" | ['h', 'e', 'l', 'l', 'o'] |
| 단어 단위 | "I love AI" | ['I', 'love', 'AI'] |
| 서브워드 단위 | "tokenizer" | ['token', 'izer'] |

각 방식에는 장단점이 있습니다. 우리는 가장 단순한 **글자 단위**부터 시작해서,
점점 더 똑똑한 방식으로 발전시켜 나갈 것입니다.

---

## 4. 토크나이저가 하는 일 두 가지

토크나이저는 두 가지 방향으로 동작합니다.

### 인코딩 (Encoding) — 문장을 숫자로

```
"hello"  →  [104, 101, 108, 108, 111]
```

AI 모델에게 문장을 입력할 때 사용합니다.

### 디코딩 (Decoding) — 숫자를 문장으로

```
[104, 101, 108, 108, 111]  →  "hello"
```

AI 모델이 출력한 숫자를 다시 사람이 읽을 수 있는 문장으로 변환할 때 사용합니다.

---

## 5. 왜 글자 하나하나로만 쪼개면 안 될까?

글자 단위 토크나이저는 구현이 매우 간단합니다. 하지만 실제 AI에서는 잘 사용하지 않습니다. 이유가 무엇일까요?

### 문제 1 — 시퀀스가 너무 길어진다

"I love artificial intelligence"라는 문장을 글자 단위로 쪼개면 31개의 토큰이 됩니다.
단어 단위로 쪼개면 4개입니다.

AI는 토큰을 하나씩 처리합니다. 토큰이 많을수록 처리 시간과 메모리가 더 필요합니다.

### 문제 2 — 의미 있는 단위를 잃어버린다

"apple"이라는 단어는 하나의 의미 덩어리입니다.
하지만 글자로 쪼개면 'a', 'p', 'p', 'l', 'e'가 되고, 각 글자는 아무 의미도 없습니다.

AI가 언어를 배우려면, 의미 있는 단위로 쪼개진 데이터를 보는 것이 훨씬 유리합니다.

---

## 6. 그렇다면 왜 글자 단위부터 배우는가?

글자 단위 토크나이저는 이해하기 가장 쉽기 때문입니다.

- 복잡한 알고리즘이 없습니다.
- 토크나이저의 핵심 개념인 **어휘집(Vocabulary)**, **인코딩**, **디코딩**을 명확하게 배울 수 있습니다.
- 이 기초 위에서 단어 단위, BPE 방식으로 자연스럽게 발전할 수 있습니다.

---

## 7. 앞으로 배울 순서

```
1단계: 글자 단위 토크나이저   ← 지금 여기
        - 가장 단순한 형태
        - 어휘집, 인코딩, 디코딩 개념 습득

2단계: 단어 단위 토크나이저
        - 의미 단위로 쪼개기
        - OOV(Out Of Vocabulary) 문제 경험

3단계: BPE(Byte Pair Encoding) 토크나이저
        - tiktoken, GPT-2가 실제로 사용하는 방식
        - 글자와 단어의 장점을 모두 취하는 방법
```

---

## 정리

| 개념 | 설명 |
|---|---|
| 토크나이저 | 문장을 숫자 목록으로 변환하는 도구 |
| 토큰 | 문장을 쪼갠 조각 하나 |
| 어휘집 (Vocabulary) | 토크나이저가 알고 있는 토큰 전체 목록 |
| 인코딩 (Encoding) | 문장 → 숫자 목록 |
| 디코딩 (Decoding) | 숫자 목록 → 문장 |

---

## 다음 단계 예고 — 단어 단위 토크나이저

글자 단위 토크나이저를 완성하고 나면, 다음에는 **단어 단위 토크나이저**를 만들어볼 것입니다.

단어 단위 토크나이저는 공백을 기준으로 문장을 쪼갭니다.

```
"I love AI"  →  ['I', 'love', 'AI']  →  [0, 1, 2]
```

이때 중요한 질문이 생깁니다.

> "만약 AI가 한 번도 본 적 없는 단어가 나오면 어떻게 해야 할까?"

이 문제를 **OOV(Out Of Vocabulary) 문제** 라고 합니다.
다음 문서에서 이 문제를 직접 경험하고, 해결책을 찾아나갈 것입니다.

## 8. 문자(Character)란 정확히 무엇인가 — Unicode와 UTF-8

### "글자 하나"는 생각보다 복잡하다

우리는 지금까지 "글자 단위로 쪼갠다"고 말했습니다. 그런데 여기서 중요한 질문이 생깁니다.

> "글자 하나"가 컴퓨터 내부에서 정확히 얼마나 많은 공간을 차지할까?

직관적으로는 "글자 하나 = 바이트(byte) 하나"라고 생각하기 쉽습니다. 하지만 이것은 사실이 아닙니다.

### Code Point와 Byte의 차이

컴퓨터 세계에서 글자를 다루는 두 가지 층위가 있습니다.

**Code Point (코드 포인트)**: 전 세계의 모든 문자에 부여된 고유한 번호입니다. Unicode라는 국제 표준이 정의합니다.
- 'A' 의 코드 포인트: U+0041
- '한' 의 코드 포인트: U+D55C
- '이' 의 코드 포인트: U+C774

**Byte (바이트)**: 실제로 파일이나 메모리에 저장되는 단위입니다. UTF-8이라는 방식으로 코드 포인트를 바이트로 변환합니다.

```
글자    코드 포인트    UTF-8 바이트 수
'A'     U+0041        1바이트
'é'     U+00E9        2바이트
'한'    U+D55C        3바이트
'𝄞'    U+1D11E       4바이트  (음악 기호)
```

### Python은 Code Point 기준으로 동작한다

Python의 `str` 타입은 Unicode Code Point 단위로 동작합니다. 따라서 `len("한")` 의 결과는 1입니다. 바이트 수가 3이어도 Python은 "글자 하나"로 셉니다.

```python
text = "한"
print(len(text))           # 1  ← Python str 기준 (Code Point)
print(len(text.encode("utf-8")))  # 3  ← 실제 바이트 수
```

### 왜 이것이 중요한가

"글자 단위 토크나이저"라고 해도 어떤 기준의 글자인지에 따라 어휘집(Vocabulary) 크기가 달라집니다.

| 기준 | 영어만 처리 | 한국어 포함 |
|---|---|---|
| Python str (Code Point) | ~100개 | 수천 ~ 수만 개 |
| UTF-8 바이트 | 256개 (고정) | 256개 (고정) |

UTF-8 바이트 기준으로 쪼개면 어휘집이 항상 256개로 고정됩니다. 반면 Code Point 기준으로 쪼개면 한국어, 중국어, 일본어를 포함할수록 어휘집이 급격히 커집니다.

실제 GPT-2는 **UTF-8 바이트 기준 BPE**를 사용해서 어떤 언어든 256개 기본 단위에서 시작합니다. 이것이 GPT-2가 "모르는 글자"를 만나지 않는 이유입니다.

## 9. 실무에서 반드시 알아야 하는 Special Token

### 특수 토큰이란?

지금까지 만든 토크나이저는 "실제 글자"만 어휘집에 등록했습니다. 하지만 실무 AI 시스템에는 글자가 아닌 **특별한 목적을 위한 토큰**이 반드시 필요합니다.

이것을 **특수 토큰(Special Token)** 이라고 합니다.

### 네 가지 핵심 특수 토큰

**[PAD] — 채우기 토큰 (Padding Token)**

AI 모델은 여러 문장을 한꺼번에 처리할 때 (배치 처리) 모든 문장의 길이가 같아야 합니다. 하지만 실제 문장은 길이가 제각각입니다. 이때 짧은 문장의 빈 자리를 [PAD]로 채웁니다.

```
문장 A (길이 5): [BOS] h e l l o [EOS]  [PAD] [PAD]
문장 B (길이 2): [BOS] h i [EOS]         [PAD] [PAD] [PAD] [PAD]
```

모델은 [PAD] 위치를 무시하도록 학습됩니다. (Attention Mask라는 기법으로 처리합니다.)

**[UNK] — 미지(未知) 토큰 (Unknown Token)**

어휘집에 없는 글자나 단어가 등장했을 때, 에러를 내는 대신 [UNK]로 대체합니다. 이렇게 하면 처음 보는 글자가 나와도 프로그램이 멈추지 않습니다.

```
어휘집: {'h', 'e', 'l', 'o'}
입력: "hello!"
결과: h e l l o [UNK]    ← '!'는 어휘집에 없으므로 [UNK]
```

**[BOS] — 문장 시작 토큰 (Beginning Of Sequence)**

모델에게 "지금부터 새 문장이 시작된다"는 신호를 줍니다. GPT 같은 언어 모델은 이 신호를 받아야 문장 생성을 시작할 위치를 압니다.

**[EOS] — 문장 끝 토큰 (End Of Sequence)**

모델에게 "문장이 여기서 끝난다"는 신호를 줍니다. 이 토큰이 없으면 모델이 언제 문장 생성을 멈춰야 할지 모릅니다. GPT가 문장을 끝없이 생성하지 않는 것은 [EOS]를 출력하도록 학습되었기 때문입니다.

### 특수 토큰의 ID는 왜 항상 고정되어야 하는가

특수 토큰은 반드시 **낮은 번호의 고정된 ID**를 가져야 합니다.

```
[PAD] = 0
[UNK] = 1
[BOS] = 2
[EOS] = 3
일반 글자들 = 4번부터 시작
```

그 이유는 이렇습니다. 모델 코드의 여러 곳에서 "PAD 토큰의 ID는 0번이다"라는 사실을 직접 사용합니다. 예를 들어 Attention Mask를 만들 때 "ID가 0인 위치는 무시하라"는 식으로 씁니다. 만약 이 번호가 학습할 때마다 달라진다면 모델 전체가 오동작합니다.

## 10. Vocabulary 크기가 실무에서 중요한 이유

### vocab_size는 모델 크기를 결정한다

어휘집의 크기(vocab_size)는 단순한 숫자가 아닙니다. 이 숫자는 **AI 모델이 가져야 하는 메모리 크기**를 직접 결정합니다.

AI 모델 내부에는 **임베딩 행렬(Embedding Matrix)** 이라는 것이 있습니다. 이것은 각 토큰 ID를 수백 차원의 숫자 벡터로 변환하는 표입니다.

```
임베딩 행렬 크기 = vocab_size × 임베딩 차원(embedding_dim)

예: GPT-2 기준
  vocab_size = 50,257
  embedding_dim = 768
  → 임베딩 행렬 = 50,257 × 768 = 약 3,860만 개의 숫자
```

vocab_size가 2배 커지면 이 행렬도 2배 커집니다. 메모리 사용량이 2배가 되는 것입니다.

### 토크나이저 방식별 vocab_size 비교

| 토크나이저 방식 | 영어 vocab_size | 한국어 포함 | 문제점 |
|---|---|---|---|
| 글자 단위 (영어) | ~100개 | 수천 ~ 수만 | 시퀀스가 너무 길어짐 |
| 단어 단위 | 수십만 개 | 수백만 개 | 메모리 폭발, OOV 문제 |
| BPE | ~50,000개 | ~50,000개 | 절충안, 실무 표준 |

### BPE가 절충안인 이유

BPE(Byte Pair Encoding)는 글자 단위와 단어 단위의 장점을 모두 취합니다.

- 자주 나오는 글자 조합은 하나의 토큰으로 묶어서 → 시퀀스 길이를 줄입니다.
- 새로운 단어는 글자 조합으로 표현할 수 있어서 → OOV 문제가 없습니다.
- vocab_size를 ~50,000 수준으로 조절할 수 있어서 → 메모리가 적당합니다.

GPT-2, GPT-4, LLaMA 등 대부분의 현대 언어 모델이 BPE 계열을 사용하는 이유가 바로 이것입니다.

## 11. 토크나이저를 저장하고 불러와야 하는 이유

### 학습한 어휘집은 반드시 저장해야 한다

토크나이저를 "학습(train)"한다는 것은, 각 글자(또는 서브워드)에 특정 ID 번호를 부여하는 것입니다. 이 번호 부여 결과가 바로 어휘집입니다.

여기서 절대로 잊어서는 안 되는 규칙이 하나 있습니다.

> **AI 모델을 학습할 때 사용한 어휘집과, 나중에 추론(inference)할 때 사용하는 어휘집이 반드시 동일해야 합니다.**

왜 그럴까요? 아래 예시를 보겠습니다.

```
학습할 때의 어휘집:
  'h' → ID 4
  'e' → ID 5
  'l' → ID 6
  'o' → ID 7

만약 추론할 때 어휘집을 새로 만들면:
  'e' → ID 4   ← 순서가 달라짐!
  'h' → ID 5
  'l' → ID 6
  'o' → ID 7
```

학습할 때 "ID 4는 h를 뜻한다"고 배운 모델에게, 추론할 때 "ID 4는 e다"라고 넣으면 모델은 완전히 틀린 답을 냅니다. 마치 한국어로 훈련받은 통역사에게 갑자기 일본어 사전을 주는 것과 같습니다.

### tokenizer.json 파일로 관리하는 이유

실무에서는 학습이 끝난 어휘집을 `tokenizer.json` 파일로 저장합니다. Hugging Face의 모든 모델 저장소에는 이 파일이 반드시 포함되어 있습니다.

```
gpt2/
  ├── config.json          ← 모델 구조 설정
  ├── pytorch_model.bin    ← 모델 가중치 (학습된 파라미터)
  └── tokenizer.json       ← 어휘집 (이것이 없으면 모델을 쓸 수 없음)
```

어휘집 파일이 없으면 모델 가중치가 있어도 텍스트를 입력할 수 없습니다. 어휘집은 모델의 일부입니다.

| 토크나이저 | 문장을 숫자 목록으로 변환하는 도구 |
| 토큰 | 문장을 쪼갠 조각 하나 |
| 어휘집 (Vocabulary) | 토크나이저가 알고 있는 토큰 전체 목록 |
| 인코딩 (Encoding) | 문장 → 숫자 목록 |
| 디코딩 (Decoding) | 숫자 목록 → 문장 |
| Code Point | Unicode 기준 글자 번호 (Python str의 기준) |
| UTF-8 | Code Point를 바이트로 변환하는 방식 |
| [PAD] | 길이가 다른 문장을 맞추는 채우기 토큰 |
| [UNK] | 어휘집에 없는 글자를 대체하는 미지 토큰 |
| [BOS] | 문장 시작을 알리는 토큰 |
| [EOS] | 문장 끝을 알리는 토큰 |
| vocab_size | 어휘집 크기 — 모델의 임베딩 행렬 크기를 결정 |
| tokenizer.json | 어휘집을 저장하는 표준 파일 형식 |
